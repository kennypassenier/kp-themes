Data tables: what to build, what to lose, which defaults

One block per data-table feature, all on the same sixty incidents. A green package today tag means the block is the shipped .kp-datatable with js/datatable.js doing the work. An amber mock tag means a working imitation written for this page only: its behaviour is inline script at the bottom of this file and its extra styling is scoped to dtr- classes; it borrows package classes such as .kp-table, .kp-button and .kp-field__input but restyles none of them. A blue mixed tag says in its note which half is which. The findings and the recommendation per feature are in research/datatable/README.md. One proposed default is applied to every mock and to no package block: --kp-badge-wrap: normal, so a status badge in a narrow column keeps its word whole. In nostromo, compare the badges in the first block (which may break mid-word) with those in any mock.

The data table as it shipspackage today

Look at: package today, nothing on this block is mock. It is .kp-datatable with data-kp-page-size="10" and data-kp-cards. Type cold in the search: the status line changes to "n of 60 rows". Sort Hours open: it sorts as numbers. Now sort Severity: it sorts alphabetically (Critical, High, Low, Medium), because the framework-free channel has no way to give one column its own order. Tick the header checkbox on page 1, then go to page 2: every row on every page is ticked, although the label says "every visible row". Tick one row, then search for a site that hides it: the header checkbox stays half-ticked for a row you can no longer see. And the status line and pager sit against the table's edge, with no room under them.

Search in one column, or all of themmock

Look at: mock. One search box with an In choice beside it. Type gate with All columns: the Main gate rows come back, and so do pump-house rows whose note mentions the gate. Switch In to Site: only the site column is searched, the pump-house rows drop out, and the matches are marked in that column only. Filters: choices, ranges, datesmock

Look at: mock. Filters opens a panel, shown open here; press it to close and open it again. The panel has the three kinds Kenny asked about: choices (Status and Severity as checkboxes, Site as a select), a range (Hours open, from and to) and dates (Opened, from and to). It starts with Open and Watching ticked, a proposed default that hides closed incidents. Every active filter appears as a removable pill under the toolbar; the count on the button matches the pills. Remove a pill: the matching control in the panel unticks or empties. Set the hours range the wrong way round (from 100 to 10) and see that the page says so rather than showing nothing. The controls are the package's own: the hours are text fields that take digits (type ten and the field says it wants whole hours), and each Opened bound is a .kp-datepicker; type 01/09/2026 or use its calendar, then remove the Opened pill and check that both pickers empty.

    Adding a filter, one at a timemock

    Look at: mock behaviour built from package parts: the button is .kp-button, the column list a .kp-menu in a .kp-popover, the editor holds .kp-field__check boxes, two .kp-field number fields or two .kp-datepicker pickers (attached by js/datepicker.js), and every active filter is a .kp-tag pill. Only the editor's frame is mock: a .kp-card or .kp-popover cuts off an open calendar in cyberpunk, whose cut corner is a clip-path. The two frozen pictures on top show the menu and an editor open; the live table below them starts with one pill, Status: Open, Watching. Compare it with the panel in the block above. Space: the panel, while open, spends its full height above the table even with nothing set (closed, its choices are out of sight too); this design spends one toolbar line and one line of pills, and the editor's height only while you edit (the line under the table measures both in the current theme). What each makes easy: the panel shows every filter at once, so you see what could be narrowed without opening anything; adding a filter keeps the toolbar quiet and does not grow with the number of columns, which matters for a table with twenty columns rather than six. Try: press + Add filter, choose Hours open, type 10 and 100, Apply: a pill Hours open: 10–100 appears and the rows narrow. Click the pill's text: its editor opens with 10 and 100 in it. Open the menu again: Status and Hours open are marked filtered, and choosing one opens its pill's editor rather than a second pill. Add Opened from 1 September with the calendar button. With two or more pills, Clear all appears. Remove a pill with its ×. Cancel and Escape leave everything as it was; an empty editor applied removes its filter.

        Sorting on more than one columnmock

        Look at: mock. It opens sorted by Severity high to low, then Hours open high to low; the small numbers in the headers give the order, and the sentence above the table says it in words. A plain click on a header replaces the sort with that one column; Shift + click (or Shift + Enter on the focused header) adds the column as the next key, and a third Shift + click on it removes it. Severity sorts in its own order here (Critical, High, Medium, Low), which the package today cannot do. Check whether the numbers read clearly beside the theme's arrow glyph, and whether Shift is discoverable enough to be worth building at all.

        Incidents, sorted on several columns. Shift and click a column header to add it to the sort.

        Choosing which columns showmixed

        Look at: mock behaviour on package classes: the menu is a .kp-menu in a .kp-popover, the checkboxes are .kp-field__check. The first copy is frozen open so every theme can be judged without clicking; the Columns button opens the live copy, and both drive the same table. Untick Note and Owner: the columns go, the header and cells together. Reference cannot be hidden, because a row without its key cannot be told apart. The package today only has .kp-col-low, which hides a marked column when the table is narrower than 40rem; a reader cannot choose.

            Row densitymixed

            Look at: the table is the package today, and so is the attribute that makes it compact: data-density="compact" from css/_density.css, set on the .kp-datatable. Only the two radio buttons are mock. Switch between them and read the measured row height under the table. Check that Compact still leaves the checkbox and the badge comfortable to hit and read. Then look at the search box and the pager: the readout shows the row losing about 8 px and the pager's buttons shrink with it, while the search box keeps its height, because .kp-datatable__search pads with literals that the density switch does not reach. Decide whether compact should reach them too.

            Pages, page size and where you aremock

            Look at: mock. Compare with the package's pager in the first block, which offers Previous, "1 / 6" and Next only. Here the footer says Showing 11–20 of 60, a Rows per page choice offers 10, 25, 50 and All, and the pager has First, Previous, numbered pages with a gap, Next and Last.             Selection with actions on the selected rowsmixed

            Look at: the table and its checkboxes are the package today; the action bar above it is mock, listening to the package's kp-datatable-select event. Three rows start selected so the bar is visible. It says how many are selected, offers Assign to, Mark closed and Clear selection, and disappears when nothing is selected. Press Mark closed: the badges on those rows change and the bar clears. Then tick the header checkbox: the count jumps to 60, not 10, because the package selects every filtered row on every page, which the React channel does not do (it selects the page). Decide which of the two it should be; the count in the bar makes the difference impossible to miss.

            Export what you are looking atmock

            Look at: mock. The preview below the table is exactly what Download CSV writes: the rows the search leaves, in the current sort, every page and not only the one on screen.             Rows that come from a servermock
            
                
            
                    Look at: mock; the "server" is a function on this page that answers after 250 to 900 ms, or 2 s with
                    Slow network on. The table does not filter, sort or page by itself: every change sends a request, logged newest first under
                    the table with its query string. Type pump house quickly: the search waits 300 ms after the last key, so one request goes
                    out, not nine. Click sort headers fast with Slow network on: an answer that arrives after a newer request was sent is thrown away
                    and the log says so. While waiting, the old rows stay dimmed and the status says it is loading. The package today has no
                    framework-free equivalent (only the React channel's totalRows).

              Moving through cells with the arrow keysmock
              
                
              
                    Look at: mock. This table is role="grid": Tab enters it once, on one cell, and leaves it with the next
                    Tab. Inside, the arrow keys move a cell at a time, Home and End go to the start and end of the row, Ctrl + Home and Ctrl + End to
                    the first and last cell, Page Up and Page Down five rows. The line under the table says where you are. Check that the focus ring
                    is visible on every cell in every theme. Then weigh it: in a grid a screen reader stops reading the table as a table and expects
                    spreadsheet behaviour, which is a promise a read-only list does not need to make.

              The proposed defaults, togethermock
              
                
              
                    Look at: mock, one table with every default the README proposes switched on and nothing else: search with an
                    In choice (all columns first), a Status filter, sorted by Opened newest first on a two-state sort, 25 rows a page
                    with 10, 25, 50 and 100 on offer, a header that stays while the 22rem box scrolls, comfortable density, and the footer inset from
                    the edge. Selection, expansion, export, inline edit and the keyboard grid are off, because they are per-app choices. Judge it as
                    the table an app would get by writing the least markup: is anything missing you would expect on day one, or anything here you
                    would switch off?
