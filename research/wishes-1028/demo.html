Eleven wishes built in the package

Almanac, homelab, chassis-rs and Kitchen hit the edges of the package in 11 places and you chose to build them. Each is now an option or a part of the package; this page shows all of them in formal only, one section per wish, on the apps’ own data (Kitchen’s dishes and steps, Almanac’s calendars, homelab’s stacks; the times and counts are mock). Everything is opt-in except two, which say so: a valid form is no longer sent by the browser, and a narrow run timeline scrolls inside its frame. 11 sections, 11 pairs.

Every section says under Expected what you should see and what each control does.

What is asked (almanac 9): The "N new" pill (data-kp-follow) only watched the direct children of its scroller, so a data table inside it never counted. With data-kp-follow-rows="tbody" it counts the rows that arrive in the table body. Is that what the Deliveries page of Almanac needs, and is "a row counts once" the right rule when a sort brings rows back?

Deliveries arriving while you read older ones

Almanac’s Deliveries table in a box that scrolls. Scroll away from the newest row, add deliveries, and the pill counts them. Sorting puts the same rows back in a new order: that is not new.

Expected:

  • At the newest row: add a delivery and it appears, the box follows it, there is no pill. Read older rows scrolls up; add three deliveries and the pill says 3 new deliveries with the way back.
  • Sort by source redraws every row in a new order and the count stays the same. Pressing the pill (or Back to the newest) scrolls to the end and the pill leaves.

Formal is a paper plate. The pill sits on the box, over the rows, in the page’s button look; the count is the exact number. The table header must not hide it.

A mapping profile and a deploy script

Almanac’s mapping profile (TOML) and its version check (bash) in the package’s code block. Switch the text, take the colour away, and walk the block’s own states.

Expected:

Is prevented the right default?

Log a bad day

Kitchen’s bad-day form. Send a valid or an empty form; the log says whether the page’s handler ran and whether the browser would have submitted (the page stops it either way, so the demo never reloads).

Expected:

  • Prevented (new default): a valid form logs kp-form-valid, the browser submit was stopped. Allowed: the browser would also have submitted: yes. An empty form shows the summary with its links and logs invalid in both.
  • Server refuses shows the server’s message on the field and the summary; accepts ends the busy Save after a moment.

The summary, the field messages and the busy button are the approved form look; the log under the form is the page’s own.
