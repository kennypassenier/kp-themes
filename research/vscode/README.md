# A VS Code colour theme from kp-themes

Kenny, 2026-09-17: "ik wil ook eens nadenken over een vs-code thema dat we uit onze thema's kunnen maken, maak daar indien mogelijk een demo van gebaseerd op cyberpunk".

It is possible, and it is built: `generate.mjs` reads `themes/<name>/tokens.json` and the derived states in `css/themes.css`, and writes a colour theme VS Code loads. The code colours come from the same table as the documentation site's highlighter (`TOKEN_TOKENS` in `gates/site/highlight.mjs`), so code looks the same in both places. `extension/` holds KP Cyberpunk, packaged as `kp-themes-vscode-0.0.1.vsix` (10,544 bytes, `wc -c`). `all/` holds the same generator's output for all 22 themes, and `demo.html` switches between them.

## Recommendation

**Adopt the generator for all 22 themes, and move it into `gates/` beside the HA generator with a `--check`, once Kenny has used KP Cyberpunk for a while.** The colour language carries over completely. Nothing typed twice: a token change reaches VS Code with the next run. What stays behind is everything in the register that is not a colour.

**What I decided (Kenny can overturn any of it).** The status bar is the theme's hero surface (`surface-hero-bg`, ink on yellow); its remote item is the hero's inverted button. The editor background is `--background`, the side bar and activity bar `--sidebar-background`, and inactive tabs `--card`. A selected list row is `.kp-tree`'s own wash (the primary at 14%). A hovered menu item is `.kp-menu__item:hover` (the foreground at 8%). The diff line colours are `.kp-diff`'s own washes. Types take `--chart-4`, because the highlighter has no type role. Function names try `--sidebar-accent-foreground` first. In 13 of 22 themes, cyberpunk among them, no candidate was both readable and distinct from the other roles, so they stay in the foreground, as on the site. Git: added and untracked green, modified amber, deleted red, conflicted `--chart-4`. Text on the side bar is picked for readability, because formal and forest have a dark side bar in a light theme. ANSI colours are chosen by the nearest hue, each token used once where the theme allows. The bright ANSI colours are the same token moved 10 points of lightness towards the foreground. All other keys take VS Code's registered defaults, and many of those point back at keys set here.

**Contrast, cyberpunk (WCAG, measured by `generate.mjs --report` on the hex VS Code receives, alpha blended onto its ground).** Editor foreground 13.51:1, comments 6.36:1, keywords 16.25:1, strings 13.88:1, types 5.54:1. Foreground on a selection 5.82:1, and on the current-line highlight 11.51:1. Three pairs are under their floor: **comments on a selection 2.74:1** (under 4.5), **the selection against the background 2.32:1** and **the line highlight against the background 1.17:1** (both under 3:1 for non-text UI). VS Code's own defaults miss those two as well, measured the same way: the current-line border is #282828 on Dark Modern's #1F1F1F (1.12:1), and the selection is #264F78 (1.94:1). A line highlight at 3:1 would compete with the selection. The other 27 pairs meet their floor, including the status bar (15.60:1) and every ANSI colour (red is lowest, 5.07:1). In cyberpunk, blue and magenta are the same violet (`--chart-4`), because the theme has no blue.

**Across the 22 themes** (`--all --report`), two findings for Kenny:

- `--chart-2` as the string colour is under 4.5:1 on `--background` in seven themes: formal 3.37, light 3.49, pastel 3.14, forest 3.72, shade-light 3.64, retro 3.69 and lapis 3.96. `--chart-1` as the keyword colour is under in three: pastel 3.89, brutalism 3.06 and nostromo 3.77. The documentation site's code blocks have the same fault today on `--card`: strings are under 4.5:1 in seven themes, keywords in three.
- In phantom the git colours fall back to plain side-bar text, because none of the success, warning or destructive tokens reads on its side bar.

**What the register does that VS Code cannot.** A colour theme carries colours, nothing else:

- No notches or clip paths (`clip-path` is on 42 lines of `css/cyberpunk-register.css`). VS Code 1.137 draws its own corner radii: buttons 4px, the quick pick 12px, from `cornerRadius.*` sizes that no theme property sets.
- No glow: there is no text shadow; only `widget.shadow` and `scrollbar.shadow` take a colour.
- No uppercase spaced labels, no "— " menu prefix, no motion, no scanline texture.
- No fonts from the theme. The user sets `editor.fontFamily` and `terminal.integrated.fontFamily`, and there is no setting for the workbench font. The package ships KP Tech Mono only as `fonts/sharetechmono/sharetechmono-regular.woff2`, VS Code only reads fonts installed on the system, so the font would have to be installed first (converted to TTF where the system wants that). How close it gets: every colour decision survives, none of the shape, type or motion does.

**Loading it, without touching Kenny's setup.** I installed nothing and changed no settings. There are two ways:

- Command Palette → _Developer: Install Extension from Location…_ → `research/vscode/extension`.
- Extensions → … → _Install from VSIX…_ → `extension/kp-themes-vscode-0.0.1.vsix`.

Both command names exist in the 1.137 bundle (grep). Then run _Preferences: Color Theme_ → _KP Cyberpunk_. I have not seen the theme in a running VS Code. I checked that every key it sets exists in the 1.137 bundle.

**Before this is committed.** `node gates/check-catalogue.mjs` refuses the demo until `catalogue/pages.js` lists `research/vscode/demo.html` under "Research to look at". The demo fetches its JSON, so it needs HTTP, not `file://`.
